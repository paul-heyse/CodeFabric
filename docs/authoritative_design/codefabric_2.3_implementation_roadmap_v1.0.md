# CodeFabric 2.3 relational data-fabric implementation roadmap

## 0. Authority and boundary

This roadmap has stable artifact identity `codefabric-relational-data-fabric-roadmap`. It is
subordinate to SUITE, ONT, GEN, FAB, QRY, LIFE, and SRV. It orders capability, evidence,
decommission, measurement, and certification work but cannot weaken, reinterpret, or certify their
contracts. The active approved v5 implementation plan owns exact packet dependencies, acceptance
checks, proving commits, milestones, and decommission batches.

V2.3 is a forward-only successor to v2.2. It preserves the proved relational ontology, exact
providers, analyses, DataFusion/Delta fabric, lifecycle, and eight-form query product while
replacing the unshipped FastMCP 3 serving tail with one modern-only FastMCP 4 presentation cell.
V2.2 and earlier suites, descriptors, allocations, plans, reviews, and evidence remain immutable
history and never become live compatibility or expected-value authority.

## 1. Sequencing invariants

1. Issue all eight synchronized v2.3 masters and independently authored modern expectations before
   changing the public gRPC or FastMCP contracts.
2. Reconcile exact fresh-start activation and revalidate inherited WP29/WP30 outcomes before wire
   revision; do not restore bootstrap, ontology/model replay, latest lookup, seed state, or hashes.
3. Revise the unreleased `codefabric.cpgd.v2` source, descriptor, generated Rust/Python bindings,
   service/client, and interoperability fixtures as one target-only transaction.
4. Land one closed atomic start outcome and daemon challenge/resource/completion/cancellation
   authority before the FastMCP presentation consumer.
5. Land the exact FastMCP 4 consumer before deleting FastMCP 3, duplicate Python authority, static
   schemas, prompts, stale wire surfaces, or invalidated evidence.
6. Prove the installed supervisor-to-daemon-to-launcher-to-modern-host vertical before issuing
   independent production behavior claims.
7. Execute independently authored decoded expectations and causal faults before physical purge.
8. Measure startup, memory, guards, completion, resources, cancellation, reconnect, and N-agent
   behavior only after purge, against the preregistered method and semantic equality.
9. Execute FreshActivation and deployment census only after a post-purge release candidate exists;
   delete dormant handoff/cutover authority only after target genesis and forward repair are proved.
10. Certify all retained and successor behavior at one trusted committed HEAD. File presence,
    digests, captures, state labels, or predecessor agreement never satisfy a stage.

## 2. Capability stages

### 2.1 Stage 0 -- v2.3 authority and independent expectations (`WP43`, `M08`)

Select exactly one synchronized terminal v2.3 suite. Freeze independently authored expectations
and negative fixtures for exact pins, modern protocol admission, fixed catalog/schema, the three
UI-extension observations, atomic start, every guarded-input leg, public handles, completion,
cancellation/reconnect, two-agent isolation, redaction, performance method, and physical zero state.
Production imports and generated observations cannot author expected values. Exit only when suite
identity/predecessor closure, expectation independence, committed faults, and drift rejection pass.

### 2.2 Stage 1 -- exact startup reconciliation (`WP44`)

Retain the target-conforming supervisor, owned sockets, process runtime, sessions, fd3 launcher,
daemon composition, and generated-v2 substrate. Repair empty-head activation through the sole
command actor: uncertain append outcomes probe by durable command/transaction identity and read one
coherent exact activation event, table vector, fence, and control horizon before `Ready`. Decouple
and revalidate inherited WP29/WP30 composition without restoring predecessor semantic authority.

### 2.3 Stage 2 -- target-coherent daemon contract (`WP45`, `M09`)

Revise `codefabric.cpgd.v2` to expose `Accepted | InputRequired | Rejected`, typed bounded
challenges and daemon continuations, daemon-minted public resource handles, authorized reference
completion projection, explicit idempotent cancellation, reserved control capacity, typed safe
errors, and existing bounded watch/resource streaming. Remove normal-path prevalidation, secret
lease projection, duplicate freshness/attempt IDs, and any live v1 service only after immediate
consumers are coherent.

### 2.4 Stage 3 -- modern FastMCP 4 presentation cell (`WP46`)

Lock FastMCP 4.0.0, MCP SDK 2.1.1, and Pydantic 2.13.4 with the camel-case bridge disabled. Build
one post-fd3 application factory with one lifespan-owned hidden daemon port, operation-aware modern
admission/redaction/cancellation middleware, exactly four tools, two resource families, one narrow
authorized completion handler, native guarded input, explicit cancel/reconnect, and no prompts or
independent Python semantic/session/task/cache/resource/auth authority.

Live modern discovery may contain only the inert empty framework-owned
`io.modelcontextprotocol/ui: {}` advertisement. The CodeFabric extension registry and resolved
UI/App component catalogs remain empty and no product behavior consumes the advertisement.

### 2.5 Stage 4 -- real modern delivery (`WP47`, `M10`)

Prove the installed path:

```text
operator policy -> WorkspaceSupervisor -> codefabricd -> exact activation Ready
-> codefabric.cpgd.v2 over owned UDS -> fd3 attach-only launcher
-> installed FastMCP 4 wheel -> protocol 2026-07-28 host
```

Exercise atomic acceptance, every guard leg and denial, progress, completion, bounded public
resources, cancellation acknowledgement, observation reconnect without resubmission, restart,
two-agent isolation/fairness, lifecycle cleanup, secret redaction, and STDOUT protocol purity.
In-memory or fake-daemon tests supplement but never replace this vertical.

### 2.6 Stage 5 -- independent evidence (`WP48`)

Execute the frozen independent expectation release against decoded target behavior and committed
causal faults. Prove clean reconstruction and require faults in protocol, catalog, guard binding,
resource authorization, completion, cancellation, restart, redaction, and authority zero state to
change the named oracle result. Historical output and target-generated expected values are
forbidden comparators.

### 2.7 Stage 6 -- complete serving purge (`WP49`, DB15--DB17)

After the target consumer and independent evidence exist, remove FastMCP 3 pins/APIs, old MCP SDK
use, camel-case compatibility, global-server assumptions, normal-path Validate-then-Start,
duplicate freshness and public attempt IDs, Python resource leases/handles, static adapter schemas,
phantom prompts, rejected sessions/tasks/auth/cache/extensions/providers/transforms/UI components,
stale recipes/tests/evidence, package residue, and live v1/history reachability. Prove retained
target behavior and zero state across source, generated output, manifests, locks, rules, packages,
wheel/sdist contents, recipes, CI selectors, and clean builds.

### 2.8 Stage 7 -- post-purge measured release candidate (`WP50`, `M11`)

Re-run the four-domain release matrix and history-independence proof. Measure cold installed startup,
idle/active per-agent RSS, no-op/status and atomic-start overhead, one/max guard rounds, completion,
resource first-byte/throughput, cancellation cleanup, reconnect/restart, and N-agent fairness and
aggregate Python memory. Use raw samples and the preregistered candidate-neutral method; no
benchmark-only path ships and semantic output must remain equal.

### 2.9 Stage 8 -- FreshActivation and sole authority (`WP51`, DB18)

From no activation head, create genesis only through `ExpectedHead::Empty` and the sole command
actor. Prove exact readback, restart reconstruction, unknown-outcome reconciliation, forward repair,
one daemon/writer/UDS owner, and deployment census. Then remove dormant handoff, predecessor
comparison/cutover, reboot/rollback, bridge, seed, latest, digest-as-proof, and dual-authority
surfaces. A discovered real predecessor is a replan trigger, not permission to revive them.

### 2.10 Stage 9 -- terminal certification (`WP52`, `M12`)

At one trusted committed HEAD, rerun inherited substrate, all v5 packet oracles, DB15--DB18 zero
state, clean reconstruction, the four build domains, package/release gates, security/recovery, and
an independent implementation review. No plan/state assertion or partial green matrix certifies
the release.

## 3. Decommission order

1. Preserve immutable v2.2/v2.1/v2.0/v1.3 suite, wire allocation, plan, review, and evidence history.
2. Keep ontology/bootstrap/model/generated-schema and v1 runtime authority physically closed while
   repairing startup; never reopen them to satisfy a serving failure.
3. Land target daemon and FastMCP consumers before DB15/DB16 deletion.
4. Land independent first-principles evidence before removing invalidated evidence/gates in DB17.
5. Delete all FastMCP 3 and duplicate Python/schema/wire/package authority before performance.
6. Complete deployment census and successful FreshActivation before DB18 handoff/cutover deletion.
7. Preserve no selectable compatibility alias, fallback, translator, generated service, package
   payload, recipe, CI selector, or benchmark-only alternate route.

## 4. Proof and release

Each stage exits only through its active-plan-named executable oracles at a proving commit. Identity
digests authenticate inputs and packages but never establish semantic correctness. Semantic and
protocol proof uses independently authored decoded expectations and committed faults. Governance
and absence claims use complete candidate enumeration plus relational, structural, textual, build,
package, and live-observation evidence appropriate to the claim.

A v2.3 release is complete only when WP43--WP52, M08--M12, DB15--DB18, all final gates, clean
reconstruction, post-purge measurement, FreshActivation, restart/reconciliation, target-only zero
state, and independent review are green at the same trusted HEAD.
